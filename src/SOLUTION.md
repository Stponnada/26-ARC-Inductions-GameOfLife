# THE GAME OF LIFE + MINESWEEPER (bonus)

## The setup

This project deals with a fun civilization style simulation where blocks (say cities) are dependent on each other to survive. 
The game has 4 rules that dictate the progress of the simulation, mainly:  
> Underpopulation: Any live cell with fewer than two live neighbors dies.
> Survival: Any live cell with two or three live neighbors lives on to the next generation.
> Overpopulation: Any live cell with more than three live neighbors dies.
> Reproduction: Any dead cell with exactly three live neighbors becomes a live cell.

The goal of the project is to calculate how many cells are alive and dead, and to feed this information into the next layer of the simulation.


## Technical Decisions

I had to work through a few main technical decision with the implementation of both the tasks in this project. They were:

### Task 1
 
1) How do you loop through all the tiles around a given tile in the grid? The solution was to measure tile numbers in terms of deviations from the tile in the center, treating it as the origin, with row and column variations of {-1, 0 and 1}. This allows us to setup a two simple nested for loops, and to skip the 0,0 tile (the tile at the center; the one we are observing) with a continue statement.
2) Dealing with edges: Python deals with negative indices in lists by wrapping around to the back of the list and measuring from the end. This creates problems if rule 1 is applied naively on grid edges, since python will not throw and error, and rather incorrectly compute the status of the cell by considering cells on the other edge of the board. Therefore, hard limits on the range of row and column numbers had to be implemented, both on their minimum and maximum values, to avoid both the wrap around issue, and the issue of the count going out of bounds of the size of the list.
3) Counting alive cells: Since the entry into the list for an alive cell is 1 and dead cell is zero, we can forgo using an if loop to check if a cell is alive of dead, and tally up the number of live cells by simply adding their list entries. Dead cells contribute zero anyway.


### Task 2
1) The scaffold in this folder insisted that we read from grid but write to next_grid, never mutating grid mid-pass. Why? Since the status of a tile depends on the status of tiles around it, influencing a tile mid game has cascading effects on other tiles that haven't been computed yet, causing incorrect calculations.
2) Simplifying the rules: The 4 rules mentioned are somewhat redundant, and can be simplified in code to: 
    > If a tile is alive, and has 2 surrounding live neighbours, it stays alive.
    > If a tile has 3 surrounding live neighbours, it stays alive.


## MINESWEEPER!!!

I noticed that this simulation is essentially an unmasked version of the game Minesweeper, where a field containing landmines is masked, and mining a tile either hits a bomb (detonating it and causing you to lose the game), or tells you how many bombs are adjacent to that tile. The goal of the game is to place flags on all the bombs, and unmask every other tile.

Drawing inspiration from the game, I decided to build a simple minesweeper layer on top of the Game of Life sim, based on the following mechanics:

1) The game stacks 3 grids on top of each other. One is the true grid of mines. The second is a grid of masks, that tell us whether a tile has been revealed yet. Finally, the 3rd grid is a grid of flags, tracking where the user has placed a flag.
2) The game uses the same mechanics that we built for the original project. A mine is a live tile. Mining such a tile causes a detonation and the user loses the game.  When a non mine tile is mined, the value of count_neighbours() is printed to alert the user with the number of bombs around them.
3) CASCADE: A new feature implemented that auto clears all the tiles around a 0 tile, since it is guaranteed to be safe
4) Minesweeper maps are generated by starting with random grids and running a few iterations of evolution on it.

The game can be played in the terminal by running minesweeper.py!

A catch: One difference between minesweeper and our implementation is that minesweeper guarantees that the first tile unmasked is always safe. Ours doesnt (and arguably makes it even more realistic - life has no guarantees or something I guess).
